### H-02 本机 HTTP 服务无认证 + 通配 CORS + 可枚举 jobId，审阅接口可被跨站读写删

**位置**：`BempServer.java`

- `addCors()`：`Access-Control-Allow-Origin: *`，允许 `GET/POST/PUT/DELETE/OPTIONS`
- `handleReview()`：GET/PUT/DELETE 均无认证；PUT 可写任意合法 jobId 的审阅文档；DELETE 可删任意 jobId 的文档
- `handlePreflight()`：新增的路径预检也继承通配 CORS
- jobId 为递增的 `job-N`（可预测），`/api/job/<id>/status`、`/api/entry/...` 可被同源策略之外的网页读取
- review 文档路径只校验字符，不校验 job 是否真实存在

**触发场景**：用户浏览器打开恶意网页，页面直接 `fetch('http://127.0.0.1:18765/api/review/job-1', {method:'PUT', ...})` 或枚举 `job-1..N` 读取状态/反编译源码，删除审阅记录。Loopback 绑定不能阻止浏览器发起请求，通配 CORS 又允许读取响应。

**影响**：本地包源码、差异树、审阅备注、审计标记可被读取/篡改/删除；攻击者还可写大量 8MB 审阅文档占满用户磁盘。

**修复（至少全部落实）**：

1. 取消 `*`，只允许 Electron/开发服务器实际 Origin；同源提供 webui 时根本不需要 CORS。
2. 启动时生成随机会话 token，通过 preload 注入渲染进程，所有 `/api/*` 请求带 `X-BempDiff-Token`；服务端统一校验，包括 review/preflight/status/entry。
3. 校验 `Origin`/`Sec-Fetch-Site`；拒绝无 Origin 的非本机请求。
4. jobId 改为 UUID/随机 ID；review PUT/GET/DELETE 校验 job 是否存在（或校验 review 文件与已知 job 的归属）。
5. 为 review 总文件数/总字节数设上限并做保留策略。

**修复结果（2026-11-25）**：

- `BempServer` 每次启动生成 32 字节随机 token（显式参数 > `-Dbempdiff.apiToken` > `BEMPDIFF_API_TOKEN` > 自动生成）；所有 `/api/*` 统一校验 `X-BempDiff-Token`、HttpOnly+SameSite=Strict 会话 Cookie 或 GET 直链 `token` 参数，缺失/错误返回 401。
- 首页 `GET /` / `/index.html` 下发 `BEMPDIFF_SESSION` Cookie，浏览器 `<a download>`、`window.open` 无需额外 header；Electron 主进程生成同一 token，经 sidecar 环境变量与 preload 同步给渲染进程。
- `routeApi` 统一拒绝非 loopback Origin、`Sec-Fetch-Site: cross-site` 和同机非白名单端口（仅本进程端口、`BEMPDIFF_DEV_PORT`、5173）；`OPTIONS` 不返回 CORS 许可。
- token 比较用 `MessageDigest.isEqual`；固定 CSRF 头仍独立校验，变更请求缺头 403。
- 证据：新增 `ServerAuthTest` 4/4；`ServerApiHttpTest` 13/13、`ServerCompareFlowTest` 3/3、`ServerStaticAndConfigTest` 8/8，共 28/28；前端 `api_auth.spec.js` 3/3。
- 残留：review 接口仍未强制 job 必须存在；本机恶意进程仍可读取进程环境/内存中的 token，强认证主要封浏览器跨站与无 token 调用。

### H-03 请求体先整包读入内存，8MB 限制检查得太晚

**位置**：

- `BempServer.readAll(InputStream)`：无长度上限
- `BempServer.handleReview()`：`readAll` 之后才 `if (raw.length() > ReviewStore.MAX_BODY_BYTES)`
- `handlePreflight()` 也使用 `readBody(ex)`，同样无上限

**触发/影响**：一个 `Content-Length` 很大或 chunked 的 PUT 可让服务端分配数百 MB/GB 的 `ByteArrayOutputStream`，直接 OOM；与 H-02 组合可被网页远程触发。即使最终返回 413，内存已经分配。

**修复**：先检查 `Content-Length`，读取时逐块累计并在超过 `MAX_BODY_BYTES` 时立即中止，抛 413，不要读完再判断。

```java
private static byte[] readAtMost(InputStream in, int max) throws IOException {
    ByteArrayOutputStream out = new ByteArrayOutputStream(Math.min(max, 8192));
    byte[] buf = new byte[8192];
    int total = 0, n;
    while ((n = in.read(buf)) >= 0) {
        total += n;
        if (total > max) throw new BodyTooLargeException(max);
        out.write(buf, 0, n);
    }
    return out.toByteArray();
}
```

`handleReview`/`handlePreflight`/`handleCompare` 统一使用该方法；捕获 `BodyTooLargeException` 返回 413。

### H-04 审阅行去重 O(n²)，可被一个 PUT 打满 CPU

**位置**：`ReviewStatusCalculator.normalizeLines()`

```java
List<Integer> lines = new ArrayList<>();
for (Object o : raw) {
    ...
    if (!lines.contains(n)) lines.add(n);   // O(n²)
}
```

**触发/影响**：上限 2,000,000 行；一个 8MB body 可放约 100 万个小整数，`contains` 退化为约 10^12 次比较，单线程 HTTP handler 长时间占满 CPU，前端表现为整个应用卡死。前端已改用 `Set`，服务端没有同步，形成明显的算法不一致。

**修复**：

```java
Set<Integer> set = new LinkedHashSet<>();
for (Object o : raw) {
    if (o instanceof Number n) {
        int v = n.intValue();
        if (v >= 0 && set.size() < MAX_REVIEW_LINES) set.add(v);
        else if (set.size() >= MAX_REVIEW_LINES) throw new IllegalArgumentException("lines 数量超限");
    }
}
return new ArrayList<>(set);
```

同时给 `lines` 数量设独立上限（如 100,000），不要只依赖 body 大小。

### H-05 反编译超时路径会导致许可泄漏、线程失控，Windows 上还可能覆盖降级结果

**位置**：`Decompiler.decompileOne()` / `cfrInProcess()`

具体链路：

1. `DECOMPILE_GATE.acquireUninterruptibly()` 在 `File.createTempFile` **之前**。若临时文件创建失败（磁盘满、权限、临时目录异常），没有进入 `try/finally`，许可永久泄漏。
2. `finally` 中先 `Files.delete(tmp.toPath())`，再 `DECOMPILE_GATE.release()`。Windows 上若超时的 CFR 线程仍持有该 class 文件，`delete` 抛 `IOException`，`release()` 被跳过，异常还会覆盖原本的 javap 降级结果。
3. 新超时用 `INPROC_CFR_POOL`（`newCachedThreadPool` + daemon）执行；`future.cancel(true)` 只中断等待的请求线程，CFR 线程可能继续跑。请求线程释放 gate 后，实际并发已不受 permit 限制；反复遇到恶意/畸形 class 会不断新建 daemon 线程，形成线程和 CPU 的无界增长。
4. 超时后的 javap 降级结果会写入磁盘缓存，之后即使系统恢复正常，也会永久返回签名级结果，属于缓存污染。

**触发场景**：恶意或畸形 class 让 CFR 超过 20 秒；磁盘满/临时目录不可写；Windows 文件锁。结果可能是：后续所有反编译卡在 gate、请求报错、线程数持续上涨。

**修复原则**：临时文件的生命周期必须由真正使用它的线程负责；gate 的 release 必须放在不可跳过的 `finally`。

```java
File tmp = null;
DECOMPILE_GATE.acquireUninterruptibly();
try {
    tmp = File.createTempFile("bempdiff-cls-", ".class");
    Files.write(tmp.toPath(), classBytes);
    final File taskTmp = tmp;
    Future<String> f = INPROC_CFR_POOL.submit(() -> {
        try { return cfrInProcessUnbounded(taskTmp); }
        finally {
            try { Files.deleteIfExists(taskTmp.toPath()); } catch (IOException ignored) {}
        }
    });
    try {
        return f.get(DECOMPILE_TIMEOUT_SECONDS, TimeUnit.SECONDS);
    } catch (TimeoutException te) {
        f.cancel(true);
        throw new IOException("CFR 超时", te);
    }
} finally {
    // 请求线程不再删除可能仍被 CFR 使用的文件；由任务线程清理
    DECOMPILE_GATE.release();
}
```

另外把 `INPROC_CFR_POOL` 改为有界池（固定线程数/有界队列），或在 submit 前再加一个 in-flight 信号量；超时计数达到阈值后熔断到独立进程模式。

### H-06 取消/重新比对会清空审阅进度，取消后旧树仍可点但标记无法保存

**位置**：`store.js` `runCompare()`、`cancelCompare()`、`triggerCompare()`；`Launchpad.vue` `openSample()`

事实链：

- `runCompare` 一开始就 `resetReview()`、`resetInsights()`，但此时 `state.job`/`state.tabs` 仍是旧作业；新作业未完成前旧树还在。
- `pollJob` 在用户取消时返回 `null`，`runCompare` 却 `return true`（注释写“作业确实提交成功过”）。
- `triggerCompare()` 把 `true` 当作成功，继续 `pushCompareHistory()`；此时 `state.job` 仍是旧 job，历史条目被写成旧 jobId/旧 stats。
- `cancelCompare()` 只把 `activeCompareId=null` 并调用后端取消，不恢复旧 review，也不清空旧 job。
- 取消后用户看到的还是旧树，但 `state.review.jobId=null`；`updateReviewFileState` 生成的新标记因 `doc.jobId` 为空不会 PUT、也不会写缓存，**标记直接丢失**。
- `openSample()` 同样把 `true` 当成功：用户取消示例比对仍会收到“示例完成”的 toast。

**影响**：取消一次比对后，用户以为还在看旧结果，开始继续审阅，所有新标记都不会保存；历史记录还会指向错误作业，后续打开历史得到错误结果。审计场景下这是高风险数据丢失。

**修复**：

1. 新作业真正 accepted 前不要清空旧 review；或保存旧 review 快照，取消时恢复。
2. `runCompare` 返回结构化结果：`{ accepted, completed, cancelled, jobId }`，取消返回 `completed:false`；`triggerCompare` 只有 `completed===true` 才写历史/提示成功。
3. 取消后清空或恢复旧 `state.job`，避免“旧树 + 空 review”的错配。
4. `pushCompareHistory` 使用本次 job id，而不是 `state.job`（旧值）。
5. 增加测试：提交→立即取消、取消后标记、取消后打开历史。

### H-07 打开历史作业没有清理上一作业的报告/AI/洞察缓存，会把旧报告冒充成新作业

**位置**：`Launchpad.vue` `openRecent()` + `store.js` `generateReport()` / `loadInsights()`

`openRecent` 的 DONE 分支只设置了 `state.job/activeCompareId/oldPath/newPath/leftType/tabs/activeKey/jobProgress`，没有清理：

- `reportMd`、`reportCache`
- `aiClassify`、`aiTasks`、`aiActiveTaskId`
- `insights`
- `excludedKeys`、`archiveChildren`、`expandedArchives`
- `sameInputCompare` 等作业级状态

而 `generateReport` 的缓存键只有类别，不含 jobId；`loadInsights` 在请求返回前也不会先清空旧数据。

**复现**：比对作业 A → 生成报告（写入 `reportCache`）→ 回 Launchpad → 打开历史作业 B（DONE）→ 点“生成报告”。`generateReport` 命中 A 的缓存，界面显示 A 的报告；下载文件名却可能用 B 的 jobId。相同路径下，旧 AI 分类还会影响 B 的风险过滤/树展示。

**修复**：

```js
function resetJobScopedState() {
  state.reportMd = null
  state.reportCache = {}
  state.aiClassify = {}
  state.aiTasks = []
  state.aiActiveTaskId = null
  resetInsights()
  state.excludedKeys = {}
  state.archiveChildren = {}
  state.expandedArchives = {}
  state.sameInputCompare = false
}
```

在 `openRecent` 设置新 job 前调用；`reportCache` 的 key 加入 `jobId`；`loadInsights` 开始时先 `resetInsights()`（至少在新 jobId 与旧不同的时候）。并中止仍在跑的旧 AI 请求。

### H-08 审阅保存并发无序、失败无提示，服务端旧文档还会覆盖本地新缓存

**位置**：`store.js` `flushReview()`、`scheduleReviewSave()`、`doLoadReviewForJob()`；`api.putReview()`

具体问题：

- `flushReview` 没有串行队列/版本号；80ms debounce 后第一次 PUT 未返回时第二次编辑可发第二个 PUT，响应乱序时旧响应会把新状态覆盖。
- `reviewSaveState='error'` 只写状态，整个 `webui/src` 没有任何组件读取它；保存失败对用户完全不可见。
- `doLoadReviewForJob` 在 `server.exists === true` 时无条件应用服务端文档并覆盖本地缓存。若上次保存失败/离线编辑，重启后服务端旧文档覆盖本地较新的缓存，编辑静默丢失。
- `beforeunload` 使用 `keepalive:true`；浏览器对 keepalive 请求体通常有约 64KiB 限制，实际审阅文档很容易超过，退出前的最后保存并不可靠。

**修复**：

1. 用 promise 链或“单飞行 + 待发送最新快照”串行化保存；每次保存携带递增 `revision`，只接受最新 revision 的响应。
2. 在 UI 状态栏/审阅栏显示“保存中/已保存/保存失败（重试）”，失败时保留本地缓存并提示。
3. 服务端生成权威 `updatedAt`；加载时比较本地缓存与服务端时间，本地更新则先应用本地并重新提交，而不是无条件覆盖。
4. 退出前不要依赖大 body keepalive；改为小批量/增量补丁，或在编辑后立即保存。

### H-09 配置脱敏只看叶子段，嵌套密码和 `api.key` 会明文泄漏

**位置**：`config_semantic.js` `isSecretKey()`

```js
const leaf = path.split(/[.[\]]/).filter(Boolean).pop()
return SECRET_KEY_RE.test(leaf.replace(/["']/g, ''))
```

只检查最后一个路径段。以下都会漏脱敏：

```json
{"datasource":{"password":{"value":"P@ssw0rd"}}}
```

路径 `datasource.password.value` 的叶子是 `value`，判定为非 secret，`P@ssw0rd` 在“脱敏”模式下仍显示。

```json
{"api.key":"sk-live-..."}
```

路径字符串 `["api.key"]` 被按 `.` 拆成 `api` 和 `key`，叶子 `key` 不匹配 `SECRET_KEY_RE`，同样明文。

XML `<password><value>...</value></password>`、YAML `password: { value: ... }` 也一样。

**修复**：按路径段（而不是按字符 split）判断，任一敏感段命中即脱敏；同时覆盖 `api.key`/`api-key`/`secret`/`token`/`password` 等带分隔符形式。对敏感节点的所有子节点一并脱敏。

```js
function isSecretKey(path = '') {
  const normalized = String(path)
    .replace(/\[\s*["']?([^"'\]]+)["']?\s*\]/g, '.$1') // ["api.key"] -> .api.key
  const segments = normalized.split('.').filter(Boolean)
  return segments.some(s => SECRET_KEY_RE.test(s.replace(/["']/g, '')))
}
```

`ConfigDiffPanel` 的 `rawResult` 即使默认不显示也会在内存中保存明文；建议只在用户显式切换“显示敏感值”时再计算 raw 版本。

### H-10 CLI/异常路径仍可能声称“已接入真实模型”，审计口径不真实

**位置**：`MarkdownReport.java` + `Main.java`

```java
private boolean aiRealLlm = true;
```

`setAiRealLlm()` 只在 `BempServer` 的 AI 报告路径被调用；`Main` 的 CLI 报告从未调用：

- CLI 未配置 Key 时使用 `MockAiAnalyzer`，`summary` 非空，footer 走 `aiRealLlm=true`；
- CLI 配置了 Key 但 `stageA` 调用失败时，代码构造降级 `StageASummary`，footer 仍可能写真实模型。

**影响**：报告审计摘要会声称“真实模型产出”，实际是 Mock/降级内容；对于一个用于评审取证的工具有直接可信度问题。

**修复**：默认改为 `false`；所有调用方显式设置：

```java
rep.setAiRealLlm(analyzer instanceof HttpAiAnalyzer && stageASucceeded);
```

或把“真实/离线/降级”做成枚举传入，footer 分别渲染。增加 CLI Mock 场景的断言测试。

### H-11 构建脚本吞掉 robocopy 失败，可能产出“缺前端但仍 exit 0”的安装包

**位置**：`scripts/build_dist_input.ps1`

```powershell
robocopy ... | Out-Null
...
exit 0
```

`robocopy` 是原生程序，`$ErrorActionPreference='Stop'` 不会让退出码 >=8 自动失败；脚本没有读取 `$LASTEXITCODE`，末尾又无条件 `exit 0`。访问被拒绝（16）、磁盘满、路径不存在等都会让 webui 同步不完整，但 CI 仍然绿色。

**修复**：

```powershell
robocopy ... | Out-Null
$rc = $LASTEXITCODE
if ($rc -ge 8) { throw "robocopy 失败，退出码 $rc" }
# 0-7 是成功/有复制；1 是正常“复制了文件”
```

同时让 `-SkipFrontend` 不只看 `index.html` 是否存在，还应比较 `webui/src` 最新 mtime 与 `dist_input/webui/index.html`，或校验构建 hash；否则改完前端后跳过构建会打包旧 UI。

### H-12 编辑 hunk 备注会被静默改成 file 备注

**位置**：`DiffView.vue` `targetForRow()` / `editExistingNote()`

hunk 备注本身没有 `line`；`editExistingNote(note)` 调 `targetForRow(-1, 'hunk')`，无效行回退到 file target。保存时 `saveReviewNote` 用该 target + 原 note.id 做 upsert，结果原 hunk 备注被替换成 file scope，`hunkId/before/after` 关联丢失。

**影响**：用户只是改备注文字，审阅结论却从“某 hunk”变成“整个文件”，报告附录证据位置错误。

**修复**：

```js
function targetFromNote(note) {
  if (note.scope === 'file') return fileTarget()
  if (note.scope === 'hunk') {
    const h = hunkById(note.hunkId)
    return h ? hunkTarget(h) : null
  }
  return lineTarget(note.line)
}
```

`targetForRow` 对无效的非 file 行应返回 `null`，不要回退到 file；`editExistingNote` 优先使用存储的 note 字段重建 target，而不是按当前行索引猜。

## 3. 中优先级问题

### M-01 `ReviewStore.load()` 只捕获 RuntimeException，IO 错误会变成 500

**位置**：`ReviewStore.java`

```java
try {
    ...
} catch (RuntimeException e) {
    backupCorrupt(file);
    return emptyDocument();
}
```

`Files.readString` 对非法 UTF-8 会抛 `MalformedInputException`（IOException），权限/磁盘错误同样。结果是 GET `/api/review/{id}` 返回 500，而不是“坏文件备份 + 空文档”。用户会卡在无法打开审阅面板，且无法通过正常删除恢复。

**修复**：区分“可读但内容坏”（JSON/UTF-8）与“不可读”（权限/IO）。前者备份并返回空文档；后者返回 `exists=false` 或明确错误码，不要把异常直接抛成 500。`ReviewStoreTest` 增加非法 UTF-8 用例。

### M-02 审阅人、更新时间、manualOverride 缺省都可被客户端伪造

**位置**：`ReviewStatusCalculator.java`

- `normalizeDocument` 直接采用 body 中的 `user` 和 `updatedAt`
- `normalizeFile` 在 `manualOverride=true` 且 status 缺失/非法时默认 `REVIEWED`

**影响**：审阅记录可以声称任意审阅人/任意时间；一个字段缺失的 manualOverride 会把文件默认标成已审，审计证据不可信。

**修复**：`user` 由服务端统一取 `System.getProperty("user.name")` 或认证身份；`updatedAt` 由服务端 `Instant.now()` 生成并额外返回 `serverUpdatedAt`；manualOverride 缺 status 时默认 `UNREVIEWED` 或 400，不要默认已审。

### M-03 报告附录的 4+ 反引号代码围栏与 Markdown 渲染器不兼容

**位置**：`review_notes.js` `codeFenceFor()` + `markdown.js`

`codeFenceFor` 为包含 ``` 的备注生成 4 个及以上反引号围栏；`markdown.js` 的围栏正则只识别恰好 3 个：

```js
const m = line.match(/^```(\w*)\s*$/)
```

于是备注中的代码块不会被识别，内部 `## 标题`、表格、列表会被当成报告正文渲染。备注内容可伪造报告章节结构（不是 XSS，但是报告完整性/证据位置错误）。

**修复**：渲染器支持 3 个及以上反引号，并记录开启围栏长度，只有“不少于开启长度”的行才关闭：

```js
const m = line.match(/^(`{3,})(\w*)\s*$/)
...
if (line.trim().startsWith(fenceTicks) && line.trim().replace(/`/g, '') === '') break
```

`codeFenceFor` 关闭围栏时也应按实际反引号数量生成，而不是 `fence.length - 4`（当前只因 lang 固定为 `text` 才碰巧正确）。

### M-04 配置语义解析的“支持范围”与实际能力不一致

**位置**：`config_semantic.js`

- `CONFIG_KINDS.properties` 同时包含 `toml`/`ini`，但 `parseProperties` 把 `[section]` 行直接跳过，不同 section 的同名 key 会互相覆盖/误报 duplicate。
- YAML `- config:\n    a: 1` 中，`push({path})` 用的是 `[0]` 而不是 `[0].config`，嵌套键变成 `[0].a`，路径丢失。
- XML `parseXml` 把 `<![CDATA[...]]>` 整体删除，CDATA 中配置值变化完全不可见。
- `json5` 仅按扩展名归为 JSON，实际用 `JSON.parse`，合法 JSON5（注释、尾逗号、单引号）会解析失败并降级。
- `|2` 显式缩进、空格后 Tab、带冒号的 quoted key 等 YAML 边界没有处理。

**修复**：要么补齐解析器（section 前缀、YAML sequence parent path、CDATA 文本节点、JSON5），要么在 `CONFIG_KINDS`/UI 中明确标注“仅原始文本 diff”，不要宣称语义支持。至少先修 section 和 `- key:` 嵌套路径，这两类在企业配置中很常见。

### M-05 反编译磁盘缓存不是原子写，可能缓存半截源码

**位置**：`Decompiler.diskPutAsync()` / `diskGet()`

`diskPutAsync` 直接 `Files.write(f, ...)`，崩溃/断电会留下半截 `.dec`；`diskGet` 只判断文件存在，不校验完整性和非空，半截内容会被回填内存 LRU，后续一直使用损坏源码。

**修复**：写临时文件后原子 move；`.dec` 增加长度/校验和头；读取时校验，不合法则删除并重算。另给 `diskWriter` 队列设上限，避免大量类结果积压。

### M-06 洞察缓存不随 Job 淘汰，`fallbackFiles` 是进程级累计值

**位置**：`BempServer.java` + `AstNormalizer.java`

- `doneStatusCache/compatCache/impactCache/insightKeysCache` 只写不随 `JobStore` 淘汰清理；`doneStatusCache` 缓存整棵树，200 个历史 job 可能占用大量堆。
- `insightKeysCache` 只写不读，属于死缓存。
- `AstNormalizer.degradedCount()` 是静态累计计数；`astSummary.fallbackFiles` 直接取全局值，会把前面作业的降级数算到当前作业。

**修复**：缓存改为单条 `JobInsight` 对象按 jobId 存储并随 Job 淘汰回调清理；`insightKeys` 删除或真正复用；降级计数改为本次比对传入的计数器/快照差。

### M-07 普通 JAR 一律 L1，`expandAllForPlainJar` 变成失效配置

**位置**：`PackageParser.isJarClass`

```java
if (isJarClass) return Layer.L1;
```

这改变了旧行为：以前普通 JAR 只有 `expandAll`/`expandAllForPlainJar` 才展开。现在默认展开所有 class，配置项失效；大型 fat jar 的差异树、报告和 AI 候选会显著膨胀。

**修复**：若这是产品决策，删除/迁移 `expandAllForPlainJar` 配置与文档并补性能测试；若不是，恢复 `expandAll || cfg.isExpandAllForPlainJar()` 判断。

### M-08 预检的 50k 上限只统计文件，空目录可绕过；symlink 同路径不拦截

**位置**：`PreflightService.inspectFolder` / `samePath`

`visitFile` 才检查 `s.entries >= SCAN_ENTRY_CAP`，没有 `preVisitDirectory`。海量空目录不会触发上限，目录遍历可能极慢。`samePath` 只比较 `toAbsolutePath().normalize()`，两个指向同一文件的 symlink 不会被判为同一路径。

**修复**：`preVisitDirectory` 也计数并设上限；`samePath` 优先 `Files.isSameFile(a,b)`，异常时再回退路径比较。补空目录/符号链接测试。

### M-09 打包后的“内置示例”实际不存在，Launchpad 空态按钮会 404

**位置**：`BempServer.handleSample()` + 打包配置

服务端按进程 cwd 拼 `bempdiff/sample_src`；打包后 cwd 是 `resources`，实际查找 `resources/bempdiff/sample_src`，但 `extraResources` 只复制 `app/jre/webui/logo`，没有复制示例目录。已核对 `release/dist_input` 不存在该目录。

**影响**：安装版空态点击“示例”得到 404；开发环境正常，容易漏测。

**修复**：把 `bempdiff/sample_src` 加入 `extraResources`，服务端改为从显式 `ROOT`/资源路径解析，不依赖 cwd；RC 冒烟增加“空态示例”用例。

**修复结果（2026-11-25）**：已用 `build_dist_input.ps1 -Clean` + electron-builder 真实产出 NSIS 安装包 `release/BempDiff-0.2.0-setup.exe`（325,540,123 B，SHA256 `9463A0C9721C50F67CA4EB96A1E1187F7B0B439B1D75303D60C2E1D47D5FD135`）。安装到隔离目录后启动成功：`GET /api/sample` 返回 `InvoiceService 示例`，`sample_src/v1`、`v2` 路径位于安装目录；`preflight` 返回 `info/0 blockers`；示例比对 `DONE`，统计为修改 1、未变 2、总 3；报告生成 2,211 字符。无 Cookie / 错误 token 访问 `/api/sample` 均返回 401。测试后关闭应用，`javaw` sidecar 归零、18765 端口关闭，并静默卸载测试副本。M-09 的安装包空态冒烟关闭；仍未做代码签名与公网分发签名校验。

### M-10 前端默认并行测试仍会失败，门禁依赖人工加参数

**位置**：`webui/package.json` + 测试报告

`test:unit` 仍是 `vitest run`（默认文件并行）。本次全量通过依赖手工 `--no-file-parallelism`；默认并行报告为 7 个 Failed Suites，属于临时缓存/ENOENT 竞争。CI 或开发者直接跑 `npm run test:unit` 会复现失败，门禁不可重复。

**修复**：把 `test:unit` 改为 `vitest run --no-file-parallelism`，或修复共享临时缓存键后开启并行；两种方式都要在 CI 固定。

### M-11 取消 QUEUED 作业只置 flag，不在端点立即置 CANCELLED

**位置**：`BempServer.handleJob` case `"cancel"`

`Job.markCancelled()` 已支持 QUEUED/RUNNING，但端点只 `job.requestCancel()`，要等 worker 拿到 `compareSem` 后才 `markCancelled`。排队期间 UI 一直显示 QUEUED，后端还可能继续等待。

**修复**：`cancel` 分支先 `job.requestCancel(); job.markCancelled();`，worker 拿到许可后看到终态直接返回；同时保留 flag 供解析中途检查。

### M-12 拖拽可重复提交比对；`runCompare` 无入口 busy 防护

**位置**：`CompareBar.onDrop()` / `store.runCompare()`

`onDrop` 直接 `triggerCompare()`，不检查 `running`；`triggerCompare`/`runCompare` 也没有“已有一个 compare 在跑”的早退。双击/连续拖拽会创建两个 job，先结束的 `finally` 会把 `activeCompareId/jobProgress` 清空，破坏后一个轮询，历史也可能写错。

**修复**：`triggerCompare` 入口检查 `state.busy || state.preflightBusy` 并提示；`onDrop` 复用 `doCompare` 的保护；`runCompare` 用 `compareRunId` 令牌，只允许当前令牌修改全局状态。

### M-13 报告失败后仍可能打开旧报告；“导出 JAR”无 job 时未禁用

**位置**：`MoreMenu.vue`、`ToolBar.vue` / `generateReport()`

`generateReport` 失败时只 toast，不清空 `state.reportMd`；`MoreMenu.genReport` 随后 `if (state.reportMd) onOpenReport()` 会打开上一份旧报告。`MoreMenu.jarDisabled` 与 `ToolBar.jarExportDisabled` 都写成 `!!state.job && changed===0`，无 job 时表达式为 false，按钮仍可点，随后走到下载/错误提示。

**修复**：`generateReport` 返回 `boolean`，失败时清空或标记旧报告不可用；`genReport` 只在 `ok` 时打开；两个组件的禁用条件都改为 `!state.job || changed===0`。

### M-14 PUT 非对象 body 会被静默当作空文档，可能清空已有审阅

**位置**：`Json.parseObject` + `BempServer.handleReview`

`Json.parseObject(s)` 对 `null`、数组、字符串等非 Map 根节点统一返回 `new LinkedHashMap<>()`，不报错：

```java
return (o instanceof Map) ? (Map<String, Object>) o : new LinkedHashMap<>();
```

因此 `PUT /api/review/job-1` 传 `null` 或 `[]` 会被当成“提交一份空文档”，`ReviewStore` 正常保存，**原有审阅记录被清空**。而真正非法的 JSON 会在 `Json.parseObject` 抛异常，被外层 catch 成 500。两种客户端错误都没有得到 400。

**触发/影响**：客户端 bug、第三方脚本或跨站请求都可清空某作业的审阅记录；错误码还会误导排障。

**修复**：新增 `parseObjectStrict`，要求根节点必须是对象；`null`/数组/标量一律 400；`handleReview` 显式校验 body 非空且含 `files/jobId` 结构。测试同时覆盖 `null`、`[]`、非法 JSON 三种情况。

### M-15 审阅汇总存在整型溢出与口径不一致

**位置**：`ReviewStatusCalculator.summarize`

- `hunkTotal` 直接 `intValue` 后累加，多个大值可溢出为负数；
- manual reviewed 文件的 hunk 仍计入 `needsReviewHunks`，文件已审但 hunk 指标显示“需复核”。

**修复**：用 `long` 累加并在输出时 clamp；明确 manual override 对 hunk 统计的语义（要么全部视为已审，要么在 UI 标注“文件级已审，hunk 级未审”）。

### M-16 review 文档无保留上限，任意 jobId 可持续写入

**位置**：`ReviewStore` + `handleReview`

`ReviewStore` 只有单文档 8MB 限制，没有总文件数/总容量限制；`PUT /api/review/{任意合法 id}` 不校验 job 存在。与 H-02 组合可被网页批量写满磁盘；正常使用中旧 job 的 review 也永不清理。

**修复**：只允许真实 job 或历史 job 的 id；设置 review 总容量/数量上限，按最近使用淘汰；提供“清除审阅缓存”。

### M-17 栏宽拖拽同步写 localStorage，滚动时 deep watch 全量遍历

**位置**：`App.vue` 布局持久化 + `DiffView.onDiffScroll`

- `watch([treeW, aiW, aiResized, treeResized], saveUiLayout)` 默认 `flush:'pre'`；`startResize` 的每次 pointermove 都改 `treeW/aiW`，于是每个鼠标事件都同步执行 `localStorage.setItem`。拖拽大窗口/低配机时会出现明显卡顿和磁盘写入放大。
- `watch([() => state.tabs, () => state.activeKey, () => state.job], scheduleSaveTabLayout, { deep: true })` 对 `state.tabs` 深层遍历；`DiffView.onDiffScroll` 每个滚动事件都写 `tab.scroll`，即使有 300ms debounce，深度遍历仍会在每个滚动事件发生，标签页多/反编译内容大时会掉帧。
- `DiffView` 的滚动位置只需持久化 `key/scroll/pinned` 等浅字段，不需要遍历 `decompile` 中的大段源码。

**修复**：

```js
// 只观察布局摘要，不深层遍历
watch(

## 4. 低优先级问题

- **L-01 CSV 公式注入防护不完整**：`safeCsvCell` 只检查首字符，前导空格/换行后跟 `=` 仍可能被 Excel 解释为公式；按 OWASP 建议对 `= + - @ \t \r \n` 及前导空白后的字符统一加 `'`。
- **L-02 Markdown 表格/换行处理不一致**：`configDiffMarkdown` 用 `\|` 转义管道、`<br>` 表示换行，但 `markdown.js` 按裸 `|` 切分且会转义 `<br>`，含 `|`/多行值的配置表格会错列或显示字面 `<br>`；`inline()` 先处理 code 再处理 `**`，代码内的 `**` 会被加粗。
- **L-03 备注弹窗无焦点陷阱/焦点恢复**：`ReviewNoteEditor` 有 `aria-modal`，但 Tab 可跑到背景，关闭后焦点不回到触发按钮；对键盘用户不友好。
- **L-04 备注 ID 与截断边界**：`normalizeReviewNote` 无 id 时用 `createdAt + text.slice(0,12)` 生成，两个同目标同时间同前缀的备注可能撞 id，`normalizeFileNotes` 按 id 去重会丢一条；`capText` 用 UTF-16 `slice` 可能切坏 emoji。
- **L-05 树自动跳转不使用队列顺序**：`DiffTree` auto-next 取原始 `tree.value` 顺序，队列视图下“下一未审”不是用户看到的队列顺序；`passRiskFilter` 对未分类节点直接隐藏，分类只覆盖 topK 时可能看不到剩余文件。
- **L-06 预检对话框边界**：`canContinue` 只接受 `ok && level==='warn'`；服务端 fallback 返回 `ok=true/warn` 正常，但若出现 `ok=false/warn` 无法继续。`triggerCompare` 未防 `preflightBusy` 双击。
- **L-07 `AssetExporter.zipTree` 的路径表示依赖**：`Files.walk(root)` 的 Path 表示与 `zipOut/tmp` 的绝对/相对形式不一致时，`Path.equals` 过滤可能失效，导致把临时 zip 自身打包；当前调用者都是绝对路径所以未触发，但方法本身脆弱。空目录也不会进入 zip。
- **L-08 损坏备份可能互相覆盖**：`ReviewStore.backupCorrupt` 用秒级时间戳 + `REPLACE_EXISTING` 命名 `.bad-<时间>`；同一秒内连续损坏会覆盖上一份备份，取证价值有限。可加毫秒/随机后缀，或保留多份。
- **L-09 `DiffView.rowNotes` 的 file fallback**：无 hunk 的 fold/无效行会显示文件级备注，计数和点击行为容易被误解；应只在 `scope==='file'` 时回退。
- **L-10 Java 文本 diff 只统一换行**：`.java` 目录模式现在纳入文本 diff，但只做 `\r\n` 归一，格式化/空行变化会被计为真实修改；如产品希望“语义 diff”，需要接 AST 或明确标注“文本级”。
- **L-11 YAML block scalar/Tab 边界**：block scalar 固定按 `indent+2` 裁剪，`|2` 不支持；Tab 只在行首检测，空格后 Tab 可被当作普通内容。
- **L-12 `browse()` 空数组仍赋值**：`Array.isArray(sel) ? sel[0] : sel` 在 `sel=[]` 时得到 `undefined` 并写入路径状态；应先判断非空。
- **L-13 `MoreMenu` 在 setup 中改全局 accent**：组件每次实例化都 `state.accent=loadAccentKey()`，当前单例影响小，但属于视图初始化副作用。
